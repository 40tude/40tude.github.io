# Audit de performance 40tude.fr (25/11/2026)

## En bref

Le site est rapide à afficher (FCP 0,4 s en desktop, CLS 0) mais **le navigateur est bloqué 2 à 9 secondes juste après l'affichage**. La cause est unique : le moteur de recherche du thème Just the Docs télécharge **`/assets/js/search-data.json` (6,1 Mo, 1,6 Mo compressé)** sur **chaque page**, puis construit l'index Lunr sur le thread principal. C'est une seule tâche longue de ~9 s sur mobile simulé, 100 % dans `just-the-docs.js`. C'est le « TBT monstrueux » vu dans PageSpeed Insights et WebPageTest (TBT 2,5 s en desktop).

En différant cette indexation au premier clic dans la barre de recherche (test sur une copie locale), le score Lighthouse passe de **49 → 80 (mobile)** et **68 → 98 (desktop)** sur l'accueil, et de **69 → 99 / 70 → 100** sur un article. Le TBT tombe à 0 ms partout.

## Méthode

- Le lien PageSpeed Insights est rendu en JavaScript : seul l'en-tête était lisible (pas de données terrain CrUX, trafic insuffisant). L'API PageSpeed renvoyait « quota dépassé » et l'environnement d'audit ne pouvait pas joindre www.40tude.fr.
- Site construit depuis ce dépôt avec Jekyll 4.4.1 / Just the Docs 0.12.0 en mode production (comme le workflow GitHub Pages), servi en local avec compression, puis **Lighthouse 12** (mobile et desktop) sur l'accueil et sur l'article *How attention works (00)*.
- Limite : les ressources tierces (Google Analytics, Font Awesome sur cdnjs) n'étaient pas joignables, leurs coûts ne sont pas dans ces chiffres. Elles apparaissent dans WebPageTest (7 requêtes bloquantes dont des tierces).
- Mesures de référence reproductibles : `history.csv`, ligne `baseline (before any fix)`.

## Goulots d'étranglement

1. **Index de recherche chargé et construit sur chaque page** (cause du TBT). Dans le `just-the-docs.js` du thème, `initSearch()` est appelé dès `DOMContentLoaded` : requête de `search-data.json` (texte intégral des ~430 pages), `JSON.parse`, puis `lunr(...)` qui indexe tout. Résultat : ~1,6 Mo transférés et ~9 s de CPU sur mobile, même si le visiteur ne cherche rien.
2. **Vignettes de l'accueil trop lourdes**. Les 10 vignettes affichées à 150 px sont les images originales des articles (900×507, 100 à 180 Ko chacune) : ~1,2 Mo d'économie possible. C'est aussi ce qui retarde le LCP mobile de l'accueil (5,2 s) en saturant la bande passante.
3. **Ressources bloquantes dans le `<head>`** : `lunr.min.js`, `just-the-docs.js`, les CSS du thème, `custom.css`, et `lightbox.js` sans `defer` (~0,6 s estimées en mobile). En production s'y ajoutent **Font Awesome 5 complet** depuis cdnjs (CSS ~60 Ko + polices) pour 4 icônes, et Google Analytics.
4. **Navigation latérale géante** : le menu complet (centaines de liens) est inclus dans chaque page, d'où un HTML d'accueil de ~100 Ko et 1 100 à 2 200 nœuds DOM. Pas dramatique (19 Ko compressés) mais ça pèse sur le parsing mobile.

## Correctifs recommandés (par priorité)

### 1. Différer la recherche (gain majeur, ~10 lignes)

Copier le fichier du thème `assets/js/just-the-docs.js` (gem `just-the-docs-0.12.0`) dans le dépôt au même chemin : Jekyll utilisera cette version. Puis remplacer l'appel `initSearch();` du bloc « Document ready » par :

```javascript
jtd.onReady(function(){
  if (document.getElementById('site-nav')) {
    initNav();
    activateNav();
    scrollNav();
  }
  // Lazy search: download and index search-data.json only on first interaction with the search box
  var si = document.getElementById('search-input');
  if (si) {
    var started = false;
    var start = function(){ if (!started) { started = true; initSearch(); } };
    si.addEventListener('focus', start, { once: true });
    si.addEventListener('pointerenter', start, { once: true });
  }
});
```

Effet secondaire : la première recherche attend le téléchargement et l'indexation (1 à 2 s en desktop). Pour aller plus loin :

- Réduire `search-data.json` : `search_exclude: true` dans le front matter des pages inutiles à indexer, ou ajuster `search.heading_level` dans `_config.yml`.
- Ou remplacer Lunr par **Pagefind** (index statique découpé, chargé à la demande) généré dans le workflow GitHub Actions après `jekyll build`.

### 2. Vignettes dédiées pour l'accueil

Générer une version 300 px de large de chaque image d'illustration (`img00_thumb.webp`, ~10-15 Ko) et la référencer depuis `index.md`. Ajouter `height` en plus de `width="150"` et `decoding="async"`. Avec ImageMagick :

```powershell
# Create 300px-wide WebP thumbnails next to each article's img00*.webp
Get-ChildItem -Recurse -Path .\docs -Filter 'img00*.webp' |
  Where-Object { $_.BaseName -notlike '*_thumb' } |
  ForEach-Object {
    $out = Join-Path $_.DirectoryName ($_.BaseName + '_thumb.webp')
    magick $_.FullName -resize 300x -quality 75 $out
  }
```

Gain attendu : ~1,2 Mo de moins sur l'accueil et un LCP mobile nettement plus bas.

### 3. Alléger le `<head>`

- Remplacer Font Awesome (CSS + polices) par 4 petits SVG inline dans `_includes/nav_footer_custom.html`, et supprimer le `<link>` cdnjs de `_includes/head_custom.html`.
- Ajouter `defer` au `<script>` de `lightbox.js` dans `_includes/footer_custom.html` (il attend déjà `DOMContentLoaded`).
- Fusionner `custom.css` dans `_sass/custom/custom.scss` (mécanisme prévu par Just the Docs) pour une requête bloquante de moins.

### 4. Points secondaires

- Google Analytics est déjà en `async`. Pour gagner encore : alternative légère (Plausible, GoatCounter) ou chargement après `load`.
- Navigation latérale : si le nombre de pages explose, replier certaines sections (`nav_exclude`) ou une nav par catégorie.
- Cache : GitHub Pages impose `Cache-Control: max-age=600` sans réglage possible ; seul un CDN devant (Cloudflare) permettrait un cache long des images. Peu prioritaire.

## Comment vérifier après correction

`./tools/perf/Measure-Perf.ps1 -Label "<ce qui a changé>"` (voir `../README.md`). Indicateurs à suivre : TBT proche de 0, `search_data_kib` à 0 dans `history.csv`, poids de l'accueil sous 1 Mo.
